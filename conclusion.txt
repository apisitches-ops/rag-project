=================================================================
สรุปโปรเจกต์: Local RAG System สำหรับเอกสาร PDF ภาษาไทย/อังกฤษ
=================================================================
(ไฟล์นี้เขียนไว้ให้เจ้าของโปรเจกต์อ่านทำความเข้าใจภาพรวมทั้งหมด
 ไม่ใช่ไฟล์ที่โค้ด/สคริปต์ใดๆ ใช้งาน)


1. โปรแกรมนี้ทำอะไร
-----------------------------------------------------------------
เป็นระบบ RAG (Retrieval-Augmented Generation) ที่:
- อ่านไฟล์ PDF (ตอนนี้คือรายงานประจำปี 2567 ของ ปตท. ภาษาไทย)
- แปลงเนื้อหาเป็นชิ้นเล็กๆ (chunk) แล้วฝังเป็นเวกเตอร์ (embedding)
  เก็บไว้ใน vector database
- เมื่อผู้ใช้ถามคำถาม (ภาษาไทยหรืออังกฤษก็ได้) ระบบจะค้นหาชิ้นเนื้อหา
  ที่เกี่ยวข้องที่สุด แล้วส่งให้ LLM สรุปเป็นคำตอบ พร้อมอ้างอิงว่า
  ข้อมูลมาจากไฟล์ไหน หน้าไหน
- ถ้าคำถามไม่เกี่ยวกับเอกสารเลย ระบบจะตอบว่า "ไม่พบข้อมูล"
  แทนที่จะเดาสุ่ม (ลด hallucination)

จุดสำคัญที่สุด: ทุกอย่างรันบนเครื่องตัวเอง (local) ทั้งหมด
ผ่านโปรแกรม Ollama ไม่มีการส่งข้อมูลออกไปที่ cloud/API ภายนอกเลย
เหมาะกับข้อมูลที่ต้องการความเป็นส่วนตัว


2. ภาษาโปรแกรมมิ่งและเครื่องมือที่ใช้
-----------------------------------------------------------------
ภาษา: Python 3.11 (รันผ่าน virtual environment ในโฟลเดอร์ venv/)

Library หลัก (อยู่ใน requirements.txt):
- langchain-text-splitters : ใช้ตัดข้อความยาวๆ เป็น chunk เล็กๆ
- langchain-ollama          : ตัวเชื่อมระหว่าง Python กับ Ollama
                              (ใช้เรียกทั้ง embedding model และ LLM)
- langchain-chroma          : ตัวเชื่อมระหว่าง Python กับ Chroma
                              (vector database)
- chromadb                  : ตัว vector database เอง เก็บข้อมูลไว้
                              ในโฟลเดอร์ data/processed/chroma/
- pypdf                     : อ่านและดึงข้อความจากไฟล์ PDF
- pythainlp                 : เครื่องมือประมวลผลภาษาไทย ใช้ 2 งาน
                              (1) แก้ตัวอักษรไทยที่เพี้ยนจากการดึง PDF
                              (2) ตัดคำภาษาไทยเพื่อวิเคราะห์ประโยค
- pytest                    : ใช้รัน unit test อัตโนมัติ

โมเดล AI ที่ใช้ผ่าน Ollama (รันในเครื่อง ไม่ใช่ cloud):
- bge-m3       : embedding model (แปลงข้อความเป็นตัวเลขเพื่อค้นหา
                 ความคล้ายคลึงกันทางความหมาย) เลือกเพราะรองรับ
                 ภาษาไทยดีกว่า nomic-embed-text ที่มีอยู่แต่แรก
- llama3.1:8b  : generation model (โมเดลที่เขียนคำตอบให้)
                 เลือกขนาด 8B เพราะเครื่องมี RAM 16GB (Apple M1 Pro)
                 ถ้าใช้โมเดลใหญ่กว่านี้อาจช้าหรือรันไม่ไหว


3. โครงสร้างไฟล์ในโปรเจกต์
-----------------------------------------------------------------
rag-project/
├── data/
│   ├── raw/              เก็บไฟล์ PDF ต้นฉบับ (ไม่ถูก commit เข้า git
│   │                     เพราะไฟล์ใหญ่ ดูใน .gitignore)
│   └── processed/chroma/ ที่เก็บ vector database (ก็ไม่ commit เช่นกัน)
│
├── src/rag/              โค้ดหลักของโปรแกรม (เป็น Python package ชื่อ "rag")
│   ├── text_processing.py   ฟังก์ชัน "ล้วน" (pure function) ไม่มีการ
│   │                         เรียก network/AI เลย ประกอบด้วย:
│   │                         - normalize_text() แก้ข้อความไทยที่เพี้ยน
│   │                         - chunk_text()     ตัดข้อความเป็นชิ้นๆ
│   │                         - select_chunks()  กรองชิ้นที่คะแนน
│   │                           ความเกี่ยวข้องผ่านเกณฑ์ที่ตั้งไว้
│   │
│   ├── ingest.py             ขั้นตอน "โหลดข้อมูลเข้าระบบ": อ่าน PDF
│   │                         ทุกไฟล์ใน data/raw/ -> ทำความสะอาดข้อความ
│   │                         -> ตัด chunk -> ฝังเป็นเวกเตอร์ด้วย bge-m3
│   │                         -> เก็บลง Chroma ข้ามไฟล์ที่เคย ingest แล้ว
│   │
│   └── query.py              ขั้นตอน "ตอบคำถาม": รับคำถาม -> ค้นหา
│                              chunk ที่เกี่ยวข้อง (ผสมสองวิธี ดูข้อ 4)
│                              -> เช็คว่าเกี่ยวข้องพอไหม -> ถ้าใช่ ส่งให้
│                              llama3.1:8b ตอบ พร้อมอ้างอิงหน้า
│
├── tests/                    unit test อัตโนมัติ (รันด้วย pytest)
│                              ทดสอบเฉพาะฟังก์ชันล้วนใน text_processing.py
│                              ไม่แตะ Ollama เลย จึงรันเร็วมาก
│
├── scripts/eval30.py          สคริปต์ทดสอบความแม่นยำ 30 คำถาม
│                              (ง่าย/ปานกลาง/ยาก อย่างละ 10) รันจริงผ่าน
│                              Ollama เพื่อเช็คว่าตอบถูกไหม
│
├── docs/                      เอกสารประกอบทั้งหมด:
│   - eval-set.md              ชุดคำถามทดสอบเล็ก (5 ข้อ) + ผลตรวจสอบ
│   - eval-set-30-stress-test.md  ผลทดสอบ 30 ข้อรอบแรก + วิเคราะห์สาเหตุ
│   - improvement-log.md       บันทึกการแก้ไขทีละรอบ พร้อมคะแนนแต่ละรอบ
│   - agents/                  เอกสารสำหรับ AI agent (ไม่เกี่ยวกับผู้ใช้)
│
├── CONTEXT.md                 อภิธานศัพท์ของโปรเจกต์ (คำว่า Document,
│                              Chunk, Query, Citation ฯลฯ หมายถึงอะไร)
├── CLAUDE.md                  ตั้งค่าสำหรับ Claude Code (ไม่ต้องสนใจ)
├── requirements.txt           รายชื่อ library ที่ต้องติดตั้ง
├── pytest.ini                 ตั้งค่าให้ pytest หาเจอโค้ดใน src/
├── venv/                      Python virtual environment (ไม่ commit)
└── .scratch/rag-pdf-ollama/   spec และ ticket ต้นฉบับที่ใช้วางแผนงาน
                               (ประวัติการออกแบบทั้งหมด)


4. หลักการทำงานแบบละเอียด (Logic)
-----------------------------------------------------------------
ขั้นตอน INGESTION (เตรียมข้อมูล) - รันครั้งเดียวตอนเพิ่มไฟล์ใหม่:
  1. อ่านทุกไฟล์ .pdf ใน data/raw/
  2. เช็คว่าไฟล์นี้เคย ingest แล้วหรือยัง (ดูจาก metadata ใน Chroma)
     ถ้าเคยแล้ว -> ข้าม ไม่ทำซ้ำ
  3. ดึงข้อความออกมาทีละหน้าด้วย pypdf
  4. normalize_text(): PDF ภาษาไทยมักมีช่องว่างแทรกกลางคำแบบสุ่ม
     (เพราะฟอนต์ในไฟล์ต้นฉบับ) จึงใช้ pythainlp ตัดคำใหม่ให้ถูกต้อง
     แทนที่จะเดาด้วย regex ธรรมดา (ซึ่งเคยลองแล้วพังมากกว่าเดิม)
  5. chunk_text(): ตัดข้อความยาวๆ เป็นชิ้นละ ~500 ตัวอักษร
  6. ฝังแต่ละ chunk เป็นเวกเตอร์ด้วย bge-m3 (ทำทีละ 64 ชิ้น ไม่ทำ
     ทีเดียวหมด เพราะเคยลองส่งทีเดียว 3,800 ชิ้น แล้ว Ollama error)
  7. เก็บ (เวกเตอร์ + ข้อความ + ชื่อไฟล์ + เลขหน้า) ลง Chroma

ขั้นตอน QUERY (ตอบคำถาม) - ทุกครั้งที่ผู้ใช้ถาม:
  1. รับคำถามจากผู้ใช้ (พิมพ์ตอนรันคำสั่ง หรือโหมด interactive)
  2. retrieve(): ค้นหา chunk ที่เกี่ยวข้อง ด้วย 2 วิธีผสมกัน (hybrid):
       ก) ฝังคำถามเป็นเวกเตอร์ แล้วหา chunk ที่ใกล้เคียงที่สุด 10 อันดับ
          (วิธีนี้เข้าใจ "ความหมาย" แต่บางครั้งพลาดคำเฉพาะทาง เช่น
          สับสนระหว่าง "สินทรัพย์รวม" กับ "สินทรัพย์หมุนเวียน")
       ข) ค้นหาคำ/วลีตรงตัว (keyword) จากคำถามเพิ่มเติม เพื่อจับ
          กรณีที่วิธี ก) พลาดคำศัพท์เฉพาะทางไป แต่จะข้ามวลีที่พบ
          บ่อยเกินไป (เช่น "ตลาดหลักทรัพย์แห่ง...") เพราะถือว่า
          ไม่เฉพาะเจาะจงพอ จะสร้างความสับสนมากกว่าช่วย
  3. select_chunks(): เช็คว่ามี chunk ไหนคะแนนความเกี่ยวข้องผ่าน
     เกณฑ์ (threshold = 0.3) บ้างไหม
       - ถ้าไม่มีเลย -> ตอบ "ไม่พบข้อมูลที่เกี่ยวข้อง" ทันที
         ไม่เรียก LLM เลย (ประหยัดเวลา + กันการเดามั่ว)
       - ถ้ามี -> ไปขั้นตอนถัดไป
  4. ส่ง chunk ที่เกี่ยวข้องทั้งหมด + คำถาม ให้ llama3.1:8b โดยกำชับว่า
       - ให้ตอบด้วยข้อมูลจาก chunk เท่านั้น ห้ามเดา
       - ให้ตอบเป็นภาษาเดียวกับคำถาม (เช็คจากตัวอักษรไทยในคำถาม)
       - ให้เช็คว่า chunk ที่เลือกใช้ตรงประเด็นจริงๆ ก่อนตอบ
       - ให้บอกว่าใช้ chunk หมายเลขไหนบ้างในการตอบ (สำหรับทำ citation)
  5. แยกคำตอบกับรายการ chunk ที่ใช้ออกจากกัน แล้วแสดงคำตอบ +
     รายการอ้างอิง (ชื่อไฟล์ + เลขหน้า) ให้ผู้ใช้เห็น


5. วิธีใช้งานจริง
-----------------------------------------------------------------
ทุกคำสั่งต้องรันจากโฟลเดอร์ rag-project/ และตั้ง PYTHONPATH=src ก่อน
เพราะโค้ดอยู่ใน src/rag/ ไม่ใช่ root โดยตรง

  เพิ่มข้อมูล (รันเมื่อมีไฟล์ PDF ใหม่ใน data/raw/):
    PYTHONPATH=src ./venv/bin/python -m rag.ingest

  ถามคำถามครั้งเดียว:
    PYTHONPATH=src ./venv/bin/python -m rag.query "คำถามของคุณ"

  โหมดถามต่อเนื่องหลายคำถาม (ไม่ใส่คำถามต่อท้าย):
    PYTHONPATH=src ./venv/bin/python -m rag.query
    (พิมพ์ exit หรือ quit เพื่อออก)

  รัน unit test:
    ./venv/bin/pytest -q

  รันชุดทดสอบความแม่นยำ 30 ข้อ (ใช้เวลาราว 10-15 นาที เพราะเรียก
  LLM จริง 30 ครั้ง):
    PYTHONPATH=src ./venv/bin/python scripts/eval30.py

7. ผลการทดสอบความแม่นยำล่าสุด
-----------------------------------------------------------------
ทดสอบด้วยคำถามจริง 30 ข้อ (10 ง่าย / 10 ปานกลาง / 10 ยาก) จากเนื้อหา
ในรายงาน ปตท. จริง:
  - รอบแรกก่อนปรับปรุง: 23/30 ถูกต้อง (77%)
  - หลังปรับปรุง 3 รอบ (เพิ่ม top-k, ปรับ prompt, เพิ่ม hybrid
    retrieval, ตั้งค่า context window ให้ถูกต้อง): 28/30 (93%)

ปัญหาที่เหลืออยู่ (บันทึกไว้เป็น known limitation ไม่ได้แก้ต่อ):
  - คำถามที่ต้องเปรียบเทียบตัวเลข 3 ปีจากตารางเดียวกัน บางครั้ง
    โมเดลยังหยิบตัวเลขผิดคอลัมน์/ปี (ความไม่แน่นอนของ LLM เอง)
    วิธีแก้ที่เป็นไปได้ในอนาคต: self-consistency (ถามซ้ำหลายครั้ง
    แล้วเลือกคำตอบที่ตอบตรงกันบ่อยที่สุด) - ยังไม่ได้ทำตอนนี้


8. ข้อจำกัดที่ควรรู้ (Out of Scope ตาม spec)
-----------------------------------------------------------------
- ไม่รองรับตารางซับซ้อนแบบเต็มรูปแบบ (table-aware chunking) - ใช้วิธี
  ตัดข้อความทั่วไป (recursive character splitting) แทน
- ไม่มี web UI หรือ API server - ใช้ผ่าน command line เท่านั้น
- ไม่มีระบบจำบทสนทนาเก่า (แต่ละคำถามตอบอิสระจากกัน)
- ไม่รองรับไฟล์อื่นนอกจาก PDF
- ไม่มี OCR สำหรับหน้าที่เป็นรูปภาพล้วน (ไม่มีข้อความให้ดึง)
